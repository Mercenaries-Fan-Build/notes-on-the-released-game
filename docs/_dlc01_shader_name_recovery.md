# DLC01 shader-name recovery and MTRL repoint

**Status:** current · **Evidence:** proven (per-row grading) · **Date:** 2026-10-04

Follow-up to `docs/_dlc01_shader_triage.md`. The triage proved 2 PC-unregistered
pixel-shader hashes are cited by 219 of 1,020 DLC01 material records:

- `0xf931343a` -- 190 refs across 112 `tinygeometry_*` blocks
- `0x3973c300` --  29 refs across  10 `rocks01_*`     blocks

This doc records: (1) the brute-force name-recovery pass across every tracked
retail binary, (2) the landing strategy chosen when no name recovered, and
(3) the end-to-end verification on `game-files/vz-patch.wad`.

### 1.2 Constant-form search (PROVEN)

Driver: `scratchpad/dlc01_shader_recovery/const_search.py`. Scanned each
binary (plus every PC shader store) for the two hashes as 32-bit LE *and* BE
constants. The Xbox 360 `default.xex`, both PS3 EBOOT variants, the PC exe and
every `shader*.bin` were covered. Zero hits in either byte order anywhere.

So the hash never appears as a literal in any shipped binary. Shader-key
resolution is name-indexed at runtime; the hash is generated by
`pandemic_hash_m2` of the registered logical name inside `FUN_0084f130`.

### 1.3 Known-family candidates (PROVEN rejection)

The project's own foliage/density docs name an engine-internal instanced-tiny
family: `PgMeshTiny`, `PgMeshTinyVP`, `PgMeshTinyShadowVP`
(`docs/reverse_engineer/foliage_instancing_plan.md`,
`docs/reverse_engineer/density_render_instancing_design.md`). None hashes to
either target. Driver: `scratchpad/dlc01_shader_recovery/try_known_names.py`.
Tried 53 combinations across tiny/mesh/rock/instance/scatter/batch families,
with and without `.sho` / `_3.sho` / `_3l.sho` / `_pl` / `_sl` suffixes. All
rejected.

### 1.4 Verdict (INFERRED)

The two logical names likely exist only in a Pandemic PS3/Xbox 360
specialisation shader registry that was never ported to PC: the triage
rejection extends across the full PS3 EBOOT.elf string pool, both Xbox
decomps (retail + preview), the PC decomp, and every retail block-strings
dump. The strings may live only inside the PS3 RSX Cg or Xbox GPU
microcode-compiler databases (whose `.updb`/`.ucode` metadata the PC build
does not ship). Recovery via disassembly of PS3/Xbox binary structures that
hold shader-register tables is possible as future work; it is not required
for this landing.

Taken together: **recovery = FAILED; path-(a) shim-register cannot be built
because the logical name is unknown**. Per the task's own guidance, fall back
to path-(b) MTRL repoint with the mapping choice documented.

## 2. Landing strategy -- path-(b) MTRL repoint

### 2.1 Choice (PROVEN)

All 219 affected records are 1-tex. Measured via
`scratchpad/dlc01_shaders/dlc01_shader_refs.json`:

| Hash | Refs | Record `tex_count` distribution |
|---|---:|---|
| `0xf931343a` | 190 | `(1, 190)` |
| `0x3973c300` |  29 | `(1,  29)` |

A 1-tex PC substitute keeps the texture-slot count honest, which is required
by `Mtrl_Parse` (`FUN_00858790`): the parser reads `tex_count` and lays
out exactly that many `{hash, 0xF011157A, 0}` 12-byte texture records
(`docs/shader_store_format.md` section 6). A substitute whose expected
texture layout matches a 1-tex record is byte-safe.

**Substitute:** `PgDiffFP` = `0x343af931` (`pandemic_hash_m2("PgDiffFP")`,
verified by the triage logical-name hash table). `PgDiffFP` is itself used
by 94 DLC01 1-tex records in `vz-patch.wad` (`dlc01_shader_refs.json`), so
the substitution ships a load-bearing demonstration that this shader resolves
through `FUN_008242b0(0x800)` and renders in the DLC01 blocks.

**Loss model:** the triage §3.6 interpretation of the lost shader context --
`tinygeometry_*` tiny-mesh scatter and `rocks01_*` rock LODs -- indicates
the real shaders were likely instanced-batch / rock-LOD variants.
Substituting `PgDiffFP` loses the specialised shading (no `_sl`/`_pl` light
perms, no scatter-batch per-vertex instance id, no rock-LOD-specific
tunables). It does not lose draw-call delivery: the game draws these
meshes at `PgDiffFP` quality instead of refusing them.

### 2.2 Mapping (final)

```text
0xf931343a (unknown; 190 refs; tinygeometry_*) -> 0x343af931  (PgDiffFP)
0x3973c300 (unknown;  29 refs; rocks01_*)      -> 0x343af931  (PgDiffFP)
```

Both to `PgDiffFP`.

### 2.3 Implementation

Shipped as a one-shot Python tool because the DLC01 PC boot test is gated on
this fix today; the Rust-side landing is planned in
`.claude/plans/dlc01-shader-key-repoint-rust-landing.md` and will add
`mercs2_formats::model_edit::mtrl::repoint_container_shader_keys` (a sibling
to the existing `repoint_container_textures`) plus a
`mercs2_probe --bin shader_key_repoint` entry point.

**Tool:** `tools/dlc01_shader_key_repoint.py`. Operates on an FFCS patch WAD:

1. `ffcs_patch_wad.read_patch_wad(src)` -- parses INDX/ASET/PTHS, extracts
   each block's compressed sges stream.
2. For each block: `sges_decompress.decompress_sges_block` -> walk the entry
   table (`u32 count` + `count * (name_hash, type_hash, field_c, chunk_size)`)
   -> for each container, walk every `MTRL` descriptor leaf.
3. Each MTRL leaf is scanned for records whose u32 marker at `+104` decodes
   to high-half `tex_count in [1,10]` and low-half flags with `0x0080` set
   (same record detector the triage's extractor uses). The u32 pixel-shader
   key at `+108 + 4*tex_count` is rewritten per the `REMAP` table.
4. Container CSUM is recomputed (`crc32_mercs2`, verified equivalent to the
   Rust `crc32_mercs2` on `test` / `UCFX` / zeros / `hello world`).
5. Modified blocks are recompressed (`sges_compress.compress_sges`) and the
   WAD is rebuilt via `ffcs_patch_wad.build_patch_wad_multi`, preserving the
   CSUM-row value and meta plus the original 144-byte cert blob.

Note: a prior pass that returned only the FIRST `MTRL` descriptor leaf per
container missed 19 of 29 `0x3973c300` refs because multi-material rock
containers carry one MTRL leaf per material group. The current tool collects
every leaf (`find_mtrl_chunks`) and iterates records in all of them. The
Rust helper's current signature returns the first leaf only
(`find_chunk`); the Rust landing plan tracks the sibling `find_chunks`
upgrade this discovered.
